# Supabase CLI Setup Script — Design

**Date:** 2026-06-09
**Status:** Approved (pending spec review)

## Goal

One-command provisioning of the Supabase backend (database tables + storage bucket) for expo-ota-server, covering both a local Supabase stack (Docker, for development/testing) and a hosted Supabase project (production). Replaces the current manual setup: copying SQL into the dashboard SQL Editor and creating the bucket by hand.

## Decision

Option A from the brainstorm: a canonical `supabase/migrations/` directory using the standard Supabase CLI flow. The existing `containers/database/schema/` files remain the source for the postgres/docker-compose path; the supabase migrations are an intentional, separate copy. Drift risk accepted: the schema is stable (2 tables, 1 migration in the project's history) and the two backends already have separate code paths (`PostgresDatabase` vs `SupabaseDatabase`).

Rejected alternatives:
- Generating migrations at runtime by concatenating `containers/database/schema/*.sql` — breaks the CLI migration history; `db push` misbehaves with regenerated files.
- Making `supabase/migrations/` the single source for both backends — touches the working postgres path; out of scope.

## File Structure

```
supabase/
  config.toml                      # generated by `supabase init`, committed
  migrations/
    20260609000001_schema.sql      # releases + releases_tracking + indexes + canary_percentage
    20260609000002_storage.sql     # creates 'expo-updates' private bucket
scripts/
  setup-supabase.sh                # entry point: --local | --remote <project-ref>
```

## Migration Content

`20260609000001_schema.sql` — consolidated schema matching the current postgres schema *after* all migrations (i.e. includes `canary_percentage INTEGER NOT NULL DEFAULT 100` directly in `CREATE TABLE releases`, rather than replaying the ALTER):

- `releases`: id UUID PK default gen_random_uuid(), runtime_version, channel (default 'production'), path, timestamp, commit_hash, commit_message, update_id, size, canary_percentage (default 100).
- `releases_tracking`: id UUID PK, release_id FK → releases(id) ON DELETE CASCADE, download_timestamp default CURRENT_TIMESTAMP, platform, device_id.
- Indexes: `idx_tracking_release_id`, `idx_tracking_platform`.
- All statements idempotent (`IF NOT EXISTS` where supported).

`20260609000002_storage.sql` — bucket creation via SQL so it works identically on local and remote:

```sql
insert into storage.buckets (id, name, public)
values ('expo-updates', 'expo-updates', false)
on conflict (id) do nothing;
```

Bucket is private; the app uses the service role key (`SUPABASE_API_KEY`), which bypasses RLS, so no storage policies are needed.

## Script Behavior — `scripts/setup-supabase.sh`

Bash, `set -euo pipefail`. Two modes:

### `--local`
1. Preflight: `supabase` CLI on PATH (error with install hint if not), Docker daemon running.
2. `supabase start` from repo root (config.toml present; migrations auto-applied on start).
3. Parse `supabase status -o env` and print ready-to-copy env block:
   ```
   BLOB_STORAGE_TYPE=supabase
   DB_TYPE=supabase
   SUPABASE_URL=<API_URL from status>
   SUPABASE_API_KEY=<SERVICE_ROLE_KEY from status>
   SUPABASE_BUCKET_NAME=expo-updates
   ```
4. Never reads or writes `.env*` files — prints only; user copies into `.env.local` themselves.

### `--remote <project-ref>`
1. Preflight: CLI present, user logged in (`supabase projects list` succeeds; if not, instruct `supabase login`).
2. `supabase link --project-ref <ref>`.
3. `supabase db push` (applies both migrations, including bucket insert).
4. Print env template with placeholders for `SUPABASE_URL` (`https://<ref>.supabase.co`) and a note to fetch the service role key from the dashboard (never echoed/fetched by the script).

### Shared
- No args / `-h`: usage text.
- Idempotent: re-running `--local` on a running stack or `--remote` with migrations applied is a no-op (CLI handles both).

## Error Handling

- Missing CLI → exit 1 with `brew install supabase/tap/supabase` hint.
- Docker not running (`--local`) → exit 1 with clear message.
- Not logged in (`--remote`) → exit 1, instruct `supabase login`.
- `db push` / `start` failures propagate (no swallowing) thanks to `set -e`.

## Testing

- Manual verification (this is provisioning infra, not app code):
  1. `./scripts/setup-supabase.sh --local` on clean machine state → stack up, both tables exist, bucket exists.
  2. Copy printed vars to `.env.local`, run app, upload a release → file lands in local Supabase Storage, row in `releases`.
  3. Re-run script → no-op, exit 0.
- No Jest tests; script is glue around the CLI.

## Out of Scope

- Unifying postgres docker-compose schema with supabase migrations (option C).
- Storage RLS policies (service role key bypasses RLS).
- Seed/demo data.
- CI integration tests against the local stack (possible follow-up).
